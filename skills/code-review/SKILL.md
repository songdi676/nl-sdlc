# 代码评审

## Overview

评审围绕五个轴：正确性（对照 tasks.md 验收标准）、可读性、架构、安全、测试充分性。评审输出分级问题清单；Critical 问题必须修复后才能进入人工批准环节。评审人必须亲自读代码验证，不得信任任何二手报告——测试报告、静态扫描输出、他人的口头结论都只是线索，不是结论。

| 轴 | 检查什么 |
|---|---|
| 正确性 | 变更是否满足 `docs/plans/<feature>/tasks.md` 中本次任务的验收标准；边界与错误路径是否处理 |
| 可读性 | 命名、结构、注释是否符合项目约定；他人能否不靠作者解释读懂 |
| 架构 | 是否贴合现有设计，无越界耦合、重复实现、模块边界被破坏 |
| 安全 | 输入校验、注入、密钥与敏感信息泄露、鉴权是否到位 |
| 测试充分性 | 测试是否真实覆盖变更行为与验收标准，而非只测实现细节或只求覆盖率数字 |

级别定义：Critical = 阻断（安全漏洞、数据丢失、与验收标准不符）；Major = 必须修复；Minor = 应修复；Nit = 可选。宁可少而准，不要十行噪声淹没一条真问题；结构性问题是评审的主体，表面风格问题排在最后。

## 流程

1. 读取 `docs/plans/<feature>/tasks.md` 中本次变更涉及任务的验收标准，逐条列出清单
2. 通读 diff 与相关文件，逐条对照验收标准，给出通过/不通过结论
3. 按五轴检查，每个问题标注：级别（Critical/Major/Minor/Nit）、文件、行号、修复建议
4. 输出评审报告（`docs/reviews/` 或随 MR 评论），Critical > 0 则结论为 REJECT

验收标准逐条结论是硬要求：任何一条缺结论，评审视为未完成。测试报告只作佐证——即使报告全绿，也必须亲自读代码确认测试真的覆盖了变更。

## 输出格式

```
结论: APPROVE | REJECT
Critical: <数量>  Major: <数量>  Minor: <数量>  Nit: <数量>
- [Critical] 文件:行 — 问题描述。修复建议: …
```

问题按级别从高到低排列；同级内按影响面（安全 > 正确性 > 架构 > 可读性 > 测试）排序。每条问题必须能定位到文件与行，修复建议必须具体到怎么做，不允许「这段代码有点复杂」式空话。

## Red Flags

| 想法 | 现实 |
|---|---|
| "报告说通过了，不用细看" | 亲自读代码，报告可能是错的 |
| "Minor 问题口头说就行" | 所有问题必须落到报告，可追踪 |
| "安全类问题让安全 agent 单独看" | 评审五轴含安全，人人负责 |
| "代码是我写的，肯定没问题" | 作者对自己的假设是盲区，每处变更都过评审 |
| "测试全绿就够了" | 测试必要不充分，架构、安全、可读性问题测不出来 |
| "过几天再清理" | 清理不会自动发生，问题在合入前修完 |

## Verification

- [ ] 每条验收标准都有对应的通过/不通过结论
- [ ] 报告中每个问题可定位到文件与行
- [ ] Critical 未清零的变更不得进入人工批准环节
