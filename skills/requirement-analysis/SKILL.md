# 需求分析

## Overview

把仓库内 `docs/requirements/` 的 Markdown 需求文档转成结构化需求：用户故事、验收标准、非功能需求，作为概要设计的输入。分析必须忠实于原文，禁止臆造原文没有的需求。

结构化需求是概要设计（`docs/designs/`）的唯一输入：设计只能引用已编号的 US/AC/NFR 条目，不得凭空引用不存在的需求。本技能只做「转写与归并」，不做取舍——加需求、砍需求、扩范围都是人的决定。

## 流程

1. 收集需求文档
   - 列出 `docs/requirements/` 下相关 .md 文档；用户可指定文件名，未指定则全部通读
   - 文档缺失或不完整时停下来向用户说明，禁止把残缺输入当完整需求
2. 逐份通读，按模块归并
   - 提取功能性描述、约束、边界条件，标注所在文件与章节
   - 同一能力跨文档出现时归并为一条，不重复编号
3. 输出结构化需求
   - 按下方「输出格式」生成条目，每项标注来源文件与章节
   - 无来源标注的需求条目不允许出现在输出中
4. 处理含糊处
   - 原文含糊、冲突或缺失的地方，逐条列入「待澄清问题清单」附在输出末尾
   - 不得自行假设答案；相关条目在清单闭环前只能标注「待澄清」

## 输出格式

- 用户故事：`作为 <角色>，我想 <目标>，以便 <价值>`，每条带唯一编号 US-01…
- 验收标准：每条可验证（能写出对应的测试断言），编号 AC-01… 并与用户故事关联
- 非功能需求：性能/安全/兼容性，可量化则给出数值

输出模板：

```markdown
# 需求分析：<feature>

## 用户故事
| 编号 | 用户故事 | 来源 |
|---|---|---|
| US-01 | 作为 <角色>，我想 <目标>，以便 <价值> | docs/requirements/<file>.md §2.1 |

## 验收标准
| 编号 | 验收标准 | 关联 |
|---|---|---|
| AC-01 | <可写成测试断言的描述> | US-01 |

## 非功能需求
| 编号 | 类型 | 要求 | 来源 |
|---|---|---|---|
| NFR-01 | 性能 | 接口 P95 < 300ms | docs/requirements/<file>.md §4.2 |

## 待澄清问题清单
1. <原文含糊处 + 出处> — 待用户答复
```

编号规则：

- US/AC/NFR 分别从 01 起全局递增；编号一旦写入不得复用或重排，下游设计、tasks.md 都按这些编号引用
- 每条 AC 必须标注关联的 US 编号；每条 US 至少被一条 AC 覆盖
- 可验证性底线：每条 AC 都能写出对应的测试断言，写不出的 AC 是模糊需求，退回原文重读或进待澄清清单

## Red Flags

| 想法 | 现实 |
|---|---|
| "文档没写清楚，我自己补合理假设" | 假设进待澄清清单，不许直接写进需求 |
| "顺手把范围扩大一点" | 分析不改需求范围，扩范围是人的决定 |
| "两条需求意思差不多，合并成一条省事" | 归并只针对同一能力；不同能力的条目不得合并改写 |
| "来源标注太繁琐，省略几处没关系" | 每条需求都要能溯源，无来源条目不得输出 |

## Verification

- [ ] 每条用户故事都有来源标注（文件 + 章节）
- [ ] 每条验收标准都能映射到至少一个测试用例
- [ ] 含糊处全部进入待澄清问题清单，输出中无任何自行假设
- [ ] 非功能需求可量化的均已给出数值
